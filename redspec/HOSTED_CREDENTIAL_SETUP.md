# Hosted Test Authority Setup

This document explains how a tester creates their own hosted test authority for the AgentEnvelope examples.

Do not request or share production credentials. The tester should create a fresh test vault, domain, delegate, legitimacy state, bot key, API key, and mint material from their own test account/workspace.

The final local `.env.local` will contain:

```bash
AE_LEGITIMACY_ID=
AE_OWNER_USER_ID=
AE_MINT_MATERIAL=
AE_BOT_KEY=
AE_DELEGATE_ID=
AE_BOT_ID=
AE_API_KEY=
```

## 1. Prepare The Local Repo

```bash
npm install
cp .env.example .env.local
```

Do not commit `.env.local`.

## 2. Create A Test Workspace

1. Go to `https://agentenvelope.io`.
2. Sign in with a dedicated test account.
3. Open the workspace dropdown.
4. Create a new workspace for this assessment.
5. Copy the test account/workspace user id from the portal.
6. Put that value in `.env.local`:

```bash
AE_OWNER_USER_ID=<tester-owned user id from the portal>
```

This value must come from the tester's own hosted test account.

## 3. Create A Test Vault

1. Go to Vault.
2. Create a new vault.
3. Use a passphrase owned by the tester.
4. Do not send the vault passphrase to anyone.

The vault root stays in the browser. It must never be placed in `.env.local`.

## 4. Create A Test Domain

Inside the new vault, create a domain for the hosted tests.

Suggested baseline domain:

```text
Namespace: redspec-support
Domain id: hosted-governance-test
Kind: support
```

Use this domain when issuing delegates for the examples.

## 5. Create A Test API Key

1. Go to Account.
2. Open API keys.
3. Create or rotate an API key for the test workspace.
4. Copy it once.
5. Put it in `.env.local`:

```bash
AE_API_KEY=<tester-created portal API key>
```

This key is required for hosted delegate lookup, hosted mint, hosted verify, MCP governance tools, and delegated record registration.

## 6. Choose A Bot Id

Pick a stable public agent id label.

Suggested value:

```bash
AE_BOT_ID=redspec-support-agent
```

This is not a secret. It is the public agent id label used in mint requests and hosted record lookup.

## 7. Generate The Bot Key

After setting `AE_API_KEY` and `AE_BOT_ID`, run:

```bash
npm run portal:setup
```

The setup script generates a local bot private key if one is missing and writes it directly to `.env.local`.

The value will be stored as:

```bash
AE_BOT_KEY=<locally generated bot private key>
```

Important:

- `AE_BOT_KEY` is generated by the tester locally.
- It is not the vault root.
- It is not a portal secret.
- It is not printed by `npm run portal:setup` once generated.
- It should not be sent back unless the test explicitly requires sharing local test secrets.

The setup script also prints the bot public address. Keep that address handy for delegate configuration.

## 8. Create A Legitimacy State

If testing portal legitimacy:

1. Go to Legitimacy.
2. Create a legitimacy state scoped to the delegate or record being tested.
3. Keep it active for baseline tests.
4. Copy the `ae-legit-...` id.
5. Put it in `.env.local`:

```bash
AE_LEGITIMACY_ID=<tester-created ae-legit id>
```

For negative tests, create or modify legitimacy state as needed:

- missing legitimacy ref
- wrong-scope legitimacy ref
- suspended/denied legitimacy
- expired policy
- stale state version or hash

## 9. Issue A Test MintDelegate

1. Go to Agents.
2. Select the test domain created in Vault.
3. Click Configure delegate.
4. Configure bounds for the test case.
5. If using address-set bot policy, paste the bot public address printed by `npm run portal:setup`.
6. Attach the legitimacy state/ref when the test requires legitimacy enforcement.
7. Enter the tester-owned vault passphrase.
8. Click Issue.

Suggested baseline delegate:

```text
Allowed operations: send-message
Allowed resources: thread:*
Bot policy: address-set, using the generated bot public address
Max mints: 10
Max uses per action: 1
Action index range: 0-99
Expiry: short test window
Legitimacy: active delegate-scoped legitimacy ref
```

For negative tests, issue a fresh delegate with the exact bounds being tested:

- Wildcard injection: allow `customer:123`, then attempt `customer:*`.
- Operation overreach: allow `send-message`, then attempt `refund-override`.
- Mint race: set `maxMints = 1` or `maxMints = 2`.
- Action index bounds: use a narrow action index range.
- Revocation: issue, verify baseline mint succeeds, revoke, then retest.

## 10. Copy Delegate Outputs

After issuing the delegate, copy these from the portal's issued delegate panel or active delegate row:

```bash
AE_DELEGATE_ID=<ae-delegate-...>
AE_MINT_MATERIAL=<one-time mint material from the issued delegate panel>
```

If a local fallback file is needed for a specific example, save the full tester-issued MintDelegate JSON as:

```text
mint-delegate.json
```

Do not use a MintDelegate, mint material, API key, bot key, legitimacy id, or owner id from any other account or workspace.

`AE_DELEGATE_ID` is used to fetch the stored delegate from hosted governance.

`AE_MINT_MATERIAL` lets the local example derive an action capability after hosted mint accepts the signed request. It is local test signing material and should be treated as sensitive.

## 11. Final Local Env Shape

The tester's `.env.local` should look like:

```bash
AE_LEGITIMACY_ID=<tester-created ae-legit id>
AE_OWNER_USER_ID=<tester-owned user id from the portal>
AE_MINT_MATERIAL=<tester-created mint material>
AE_BOT_KEY=<tester-generated local bot private key>
AE_DELEGATE_ID=<tester-created ae-delegate id>
AE_BOT_ID=redspec-support-agent
AE_API_KEY=<tester-created portal API key>
```

Optional Bedrock values for LLM-backed examples:

```bash
AWS_REGION=us-east-1
BEDROCK_MODEL_ID=<bedrock model id>
```

## 12. Verify Setup

Run:

```bash
npm run preflight
npm run portal:setup
```

Then run a hosted flow:

```bash
npm run hosted:multi
```

For the escalation pressure test:

```bash
npm run hosted:escalation
```

For overreach testing:

```bash
npm run hosted:overreach
```

## 13. Repeat Per Test Case

When a test requires different policy:

1. Configure new delegate bounds in the portal.
2. Issue the delegate.
3. Update `AE_DELEGATE_ID`.
4. Update `AE_MINT_MATERIAL`.
5. Update `AE_LEGITIMACY_ID` if the legitimacy state changes.
6. Keep the same `AE_API_KEY`, `AE_BOT_ID`, `AE_BOT_KEY`, and `AE_OWNER_USER_ID` unless the test intentionally changes account, bot, or owner scope.

Each finding should name the exact delegate policy, legitimacy state, and hosted route used.
